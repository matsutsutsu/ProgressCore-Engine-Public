## 技術的なこだわり・工夫した点

- **データ指向設計（DOD）**: コンポーネントを SoA チャンクに連続配置し、キャッシュミスを抑制。構造変更は遅延キューに積んでフレーム境界でまとめて反映し、走査中の破壊を防止。
- **アニメーションのホットパス最適化**: 骨ごと・毎フレーム走っていた静的処理（ボーン種別の文字列判定・アニメ名検索・0秒基準ポーズ）を「不変値は一度だけ計算してキャッシュ」方針で削減し、`ComputeAnimation` の負荷とスパイクを低減。
- **モデルの二段ロード**: 初回に glTF を解析して独自バイナリ（`.cereal`）へ焼き、次回以降は高速ロード。
- **プロファイリング前提**: Tracy を全域に計測ゾーンとして組み込み、起動負荷や毎フレーム負荷を可視化しながら最適化。
- **データ駆動シェーダー / コンポーネントメタ**: シェーダーやコンポーネントの定義をデータ側に寄せ、追加時のボイラープレートを最小化。

## アーキテクチャ

```
FixedUpdate (60Hz) → SceneManager::FixedUpdate → ECSContext::UpdateLogic   … ゲームロジック・物理
Update             → SceneManager::Update       → ECSContext::UpdateRender … 描画準備・アニメ更新
Render             → SceneManager::Render       → Graphics::Render          … レンダーパイプライン実行
```

- `Source/Engine/` — 再利用可能なエンジン基盤（ECS / 描画 / 物理 / アニメ / UI / 音声 …）
- `Source/Game/` — ゲーム固有のロジック（プレイヤー / ボス / ドローン AI / コンバット …）
- `Source/Editor/` — ImGui ベースのエディタ UI（`ENABLE_EDITOR` ビルド時）

## コメント規約

記法は 2 つだけ。使い分けの基準を「Visual Studio が整形して表示してくれるか」に一致させている。

| 記法 | 使う場面 |
|------|----------|
| `//` | すべての説明（ファイル先頭・宣言の上・宣言の右・実装の中） |
| `/** */` | `@param` / `@return` で引数や戻り値に構造を持たせたい関数だけ |

- **Doxygen タグは `/** */` の中にだけ書く。** ドキュメント生成に Doxygen を使っていないため、タグを解釈する仕組みが無い場所に `@brief` や `@file` を付けても、読みにくくなるだけで得るものが無い。逆に `@param` は Visual Studio が引数ごとに整形して表示するので、そこだけはタグに実利がある。
- **`///` は使わない。** Visual Studio は `//` でもツールチップに表示するため `///` との差が無く、`///<` に至っては `<` がそのまま文字として表示されてしまう。
- **ファイル先頭コメントは `#pragma once` / `#include` の前**に置き、「何をするか → なぜこの分離なのか → 注意点」の順で書く。ファイル名は書かない（開けば分かるため）。
- **変数の説明は 1 行に収める。** 長い理由づけが要るときは個々の変数ではなく、構造体やセクションの先頭にまとめて書く。
- **関数コメントは名前から分からないことだけ書く**（前提条件・副作用・実行順序の制約）。`Update` / `Initialize` のような自明なものには付けない。

```cpp
// ボスの「状況認識」を Blackboard へ書き込む専用システム。
//
// 役割分担（BehaviorTreeSystem を汎用のまま保つための分離）:
//   BossPerceptionSystem（このファイル） … ボス固有の「今の状況」を認識する
//   BehaviorTreeSystem（汎用）           … blackboard を読んで判断するだけ
//
// 実行順序: L02_PreUpdate（AI の感知フェーズ）。
#pragma once
```

上記は `Source/` 配下の全 697 ファイルに適用済み。
